# План: каталог инструментов Hermes в Rust CLI

Цель — довести набор инструментов Rust CLI до набора эталона из списка ниже. Каждый инструмент проходит один и тот же путь: схема записана из эталона, поведение сверено на фикстурах, тест на имитаторе, строка в `compat/matrix.md`.

## Что уже есть

| Набор | Инструменты | Состояние |
| --- | --- | --- |
| web | `web_search`, `web_extract` | Сделано для Tavily, SearXNG и Brave. Нет Firecrawl, Exa, Parallel, Keenable, Perplexity, DDGS, режима без ключей |
| file | `read_file`, `write_file`, `patch`, `search_files` | Сделано |
| terminal | `terminal` | Сделано, включая `background=true` (параметр виден, пока предлагается `process_manage`). Нет pty, `notify_on_complete`, `watch_patterns` |
| skills | `skills_list`, `skill_view` | Сделано. Нет `skill_manage` |

## Волна 0. Основа (сделана)

Сделано: реестр `tools.rs` (таблица инструментов с условием показа и вызовом, контекст `ToolContext`, подтверждения через единый `Approver`), алфавитный порядок с тестом по записи эталона, доступность по набору и окружению, точная оценка префикса запроса при сжатии, запись из эталона и проверка абзаца про память. Не сделано: замена рукописных схем файловых инструментов, `terminal` и навыков на схемы эталона. Их описания обещают режимы, которых здесь нет (например нечёткая замена в `patch`), поэтому замена идёт вместе с реализацией этих режимов.

Исходный план шагов:

Без неё каждый новый инструмент добавляет ещё одну ветку в `match` в `turn.rs`, а мета-инструменты невозможны.

1. **Реестр инструментов.** Один трейт `Tool` (схема, набор, проверка доступности, `call(ctx, args)`), реестр вместо ручных списков в `tools_for_prompt` и диспетчере. Контекст хода (`ToolContext`): профиль, рабочая папка, идентификатор сессии, канал подтверждений и вопросов, отмена, настройки. Результат нормализуется и ограничивается по длине, как `tool_error` в эталоне.
2. **Порядок и состав.** Порядок инструментов в запросе алфавитный, как в эталоне. Фикстура `default_tools.json` уже записана, добавить тест порядка. Доступность через `check_fn`: инструмент не предлагается, если он не может работать (нет бэкенда, нет интерпретатора, отключён набор).
3. **Единый путь побочных эффектов.** Всё, что пишет на диск или запускает процессы, идёт через подтверждение и, при необходимости, отмену. Проверка в одном месте.
4. **Генератор данных из эталона.** Расширить `create_tool_schema_fixture.py`: схемы всех портируемых инструментов, абзацы prompt, зависящие от наличия инструментов (`SKILLS_GUIDANCE`, `SESSION_SEARCH_GUIDANCE` и т. д.).

Проверка: все 10 текущих инструментов работают через реестр, существующие 116 Python-тестов и Rust-тесты проходят без изменений.

## Волна 1б. Библиотека редактирования секретов (новая, нужна до `session_search` и `browser_cdp`)

`session_search` прогоняет через редактор все сообщения, которые всплывают из других сессий, а `browser_cdp` — весь вывод страницы. Эталонный редактор (`agent/redact.py` около 2000 строк и 17 соседних модулей, всего около 3800 строк) — это не набор префиксов: ключи в JSON, в аргументах командной строки, в URL, в строках подключения, в Python-repr, заголовки авторизации, PEM-ключи, JWT, телефоны и разбор вложенных структур с лимитом глубины.

Как делать:
1. Зависимость: крейт `regex` не поддерживает lookaround и притяжательные квантификаторы, которые эталон использует повсюду. Нужен `fancy-regex` (с эмуляцией атомарных групп) либо ручной разбор для самых горячих шаблонов. Решить на прототипе, измерить время на больших вводах: редактор запускается на каждом результате.
2. Корпус: генератор записывает из эталона пары «вход → выход» для сотен строк (по одной на каждый шаблон плюс граничные случаи, отрицательные примеры и вложенные структуры), Rust-тест сверяет их побайтно. Это единственный способ поймать расхождения в шаблонах.
3. Порядок: сначала префиксы ключей и присваивания (`.env`, JSON, CLI, URL), затем строки подключения и заголовки, затем структурный обход, затем остальные модули. Каждый шаг закрывается корпусом.
4. Политика включения: `HERMES_REDACT_SECRETS` и настройки профиля (`note_env_policy`, `note_config_policy`).
5. Потребители после библиотеки: `session_search`, `browser_cdp`, редактирование вопросов `clarify` и подтверждений, вывод инструментов.

Состояние (волна 1б, основной путь `force=True` перенесён): модуль `redact` на `fancy-regex`, корпус из 350 строк в 23 категориях записан из эталона (`compat/create_redaction_corpus.py`), тест `redaction_corpus.rs` требует, чтобы все строки совпадали побайтно, плюс тест на враждебных входах (до секунды на 200–300 КБ). Перенесены проходы в порядке эталона: блоки приватных ключей (PEM, base64 PEM, PGP, PuTTY, age), ключи с известными префиксами (в том числе разбитые управляющими символами и цветовыми кодами), присваивания `cookie=`, ENV (верхний и нижний регистр), конфиги (точечные и в начале строки), JSON-поля (закрытый список, экранированные, с аффиксами, заголовочные), Python-repr, YAML, флаги командной строки и ключи строк подключения Azure, заголовки авторизации, API-ключи и Cookie в заголовках (сырые строки, curl, лог, JSON), токены Telegram, пароли в URL баз данных и их параметры запроса, вебхуки, голые токены и `user:pass@` в URL, пути `//user:pass@`, строки подключения «ключ=значение», JWT, ссылки webapp, тела форм, телефоны.

Дополнительно перенесены: `key = value` с пробелами, `NAME=user:pass`, неполные приватные ключи, токены Zhipu и Discord, строгие URL (`redact_derived_text`, для текста, который выходит из сессии). Не перенесено: реестры значений хранилища и источников секретов, режимы `file_read` (маска без повторного использования), `code_file` и `secret_file`, переключатель `security.redact_secrets` (путь `force=True` его не учитывает, как и эталон). Для `session_search` библиотека готова (`redact_derived_text`); к чтению файлов её подключать нельзя, пока нет режима `file_read`.

Ограничение времени: без этого пункта `session_search` и `browser_cdp` придётся либо выпускать без редактирования (небезопасно), либо с упрощённым (расходится с эталоном). Рекомендация: не делать их до библиотеки.

## Волна 2. Отложенный каталог

`tool_search`, `tool_describe`, `tool_call`. Нужна после волны 1, потому что их основная работа — скрыть `todo_list`, `session_search`, браузер и подобные.

1. Каталог схем и поиск по нему (`tool_search_catalog.py`, `tool_search.py`), валидация аргументов перед вызовом.
2. Порог отложенной загрузки из конфига (`tools.tool_search.defer`), правила, какие инструменты скрываются.
3. `tool_call` исполняет скрытый инструмент через тот же реестр и те же проверки политики набора.

Проверка: список инструментов по умолчанию совпадает с эталоном для пустого профиля; скрытый инструмент находится поиском и вызывается; запрещённый набором инструмент не вызывается и через `tool_call`.

## Решения, которые нужны от вас

1. **`execute_code`.** (а) запускать пользовательский интерпретатор Python с RPC-мостом к инструментам Rust, как опциональный внешний процесс; (б) встроить собственную песочницу на Rust (дорого, расходится с поведением); (в) отложить. Рекомендация — (а), по аналогии с планом для плагинов.
2. **`browser_exec`.** (а) опциональный процесс с Python-обвязкой эталона и версионированным RPC; (б) собственный CDP-слой на Rust с набором команд, который задаст модель; (в) только `browser_cdp`. Рекомендация — сначала `browser_cdp` и `browser_dialog`, затем (а).
3. **Объём.** Нужны ли `manage_connections` и holographic (`fact_store`, `fact_feedback`) в первом выпуске или они остаются за рамками.
4. **Видимость по умолчанию.** Повторять скрытие `todo_list`, `session_search` и браузера через `tool_search`, или показывать их сразу. Рекомендация — повторять эталон.

## Общие правила для каждого инструмента

- Схема только из эталона, никакой рукописной копии. Тест сверяет её с фикстурой.
- Наличие в наборе определяется `toolsets.json`; новые инструменты сразу попадают под `platform_toolsets` и `agent.disabled_toolsets`.
- Побочные эффекты идут через подтверждение; в cron и one-shot они не предлагаются.
- Ошибки и URL не выдают секреты. Ввод из сети и от модели проверяется до использования.
- Один коммит на инструмент или на шаг основы: код, тесты, строка в матрице, обновление плана.
- Что не перенесено, пишется явно в плане и в `compat/matrix.md`.
