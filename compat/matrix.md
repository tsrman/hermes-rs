## Результаты чтения исходников

- Эталон использует `state.db`, SQLite schema version 33, независимую версию FTS и таблицы `runtime_epoch` и `session_admissions`. [Схема upstream](https://github.com/NousResearch/hermes-agent/blob/2f8c1e7ed051c311af4f3b3ca0f8976b9c40839b/persistence/sqlite/_schema_ddl.py)
- Lumio `SessionPersistence::new` открывает `sessions.db` и создаёт отдельную схему с `created_at`, `updated_at` и `platform`. Следовательно, автоматическую совместимость с профилями эталона считать неподтверждённой. [Исходник Lumio](https://github.com/Lumio-Research/hermes-agent-rs/blob/9a145877cacfde43efa07115536b71c51344de75/crates/hermes-agent/src/session_persistence.rs)
- Ultra `SessionPersistence::new` также открывает `sessions.db`. Совместимость остальных путей доступа и миграции требует отдельной проверки. [Исходник Ultra](https://github.com/sheawinkler/hermes-agent-ultra/blob/v0.22.0/crates/hermes-agent/src/session_persistence.rs)
- Lumio указывает эталон `v2026.4.13`, Ultra в своей опубликованной матрице указывает upstream `5e51b123f32b7f6a51fbd5759e89ba5146ce4003`. Эти проверки относятся к другим версиям upstream. [Lumio README](https://github.com/Lumio-Research/hermes-agent-rs/blob/9a145877cacfde43efa07115536b71c51344de75/README.md), [матрица Ultra](https://github.com/sheawinkler/hermes-agent-ultra/blob/v0.22.0/docs/parity/parity-matrix.md)

Сравнительный тест `session_import.rs` на свежем профиле Python для Lumio завершился ошибкой `no such table: messages`. `load_session` открыл `sessions.db`, отсутствовавший в исходном профиле. Пять собственных модульных тестов `session_persistence` Lumio прошли, однако они создают профиль Lumio и не проверяют импорт профиля Python. Общий запуск с фильтром `session_persistence` был прерван во время последующего property-теста, поэтому результат относится только к этим пяти модульным тестам. Команды воспроизведения приведены в `compat/README.md`.

Тот же тест для Ultra завершился несовпадением результатов. `load_session` вернул пустой список вместо двух сообщений Python. Это подтверждает расхождение конкретного API хранения, а проверка штатной команды `--resume` остаётся отдельной задачей.

Проверка собранных CLI показала, что оба порта отклоняют `hermes chat --resume compat-session` как неизвестный параметр. У Ultra есть отдельная команда `resume`. При её запуске в терминале на чистом профиле Python она завершилась ошибкой отсутствующего каталога `sessions/`, который предназначен для файлов сессий Ultra. Поддержка других способов импорта в этих наблюдениях не проверялась.

Один и тот же локальный сценарий `read_file` выполнен через `AIAgent.run_conversation` эталона и `hermes chat -q` обоих Rust-портов. Все три получили финальный ответ после передачи результата инструмента модели. Python отправил результат с полями `content`, `total_lines`, `file_size`, `truncated`, `is_binary`, `is_image`, `not_found`. Lumio и Ultra передали объект с единственным полем `result`. Эталон вызывался с отключённой памятью и локальными инструкциями, порты запускались со своими настройками по умолчанию. Поэтому число объявленных инструментов и prompt пока не являются сопоставимым измерением паритета. Lumio использовал модель `fixture`, Ultra заменил её на `gpt-5.5-pro`.

Rust-реализация в этом репозитории использует собственный Cargo workspace. Расхождения кандидатов в формате хранения, штатном `--resume` и результате `read_file` учитывались при выборе базы. Файлы профиля для экспериментов должны находиться во временных каталогах.

## Один ход в Rust CLI

На сценарии `tool` Python и Rust сохранили одну и ту же последовательность ролей. Первое обращение передало `system, user`, второе добавило `assistant, tool` с результатом чтения. Текст системного сообщения у каждого клиента совпал между его двумя запросами.

При лимите в две итерации оба клиента передали два результата `read_file`, затем добавили запрос на сводку, сохранив историю и определения инструментов. Python вернул `completed=false` с причиной `max_iterations_reached(2/2)`. Rust выводит сводку и возвращает код `1`.

В `stall` прерывание после начала запроса остановило оба клиента до следующего запроса. Python вернул `interrupted_during_api_call`, Rust CLI вернул код `130`. В `partial_tool` Python исполнил `read_file` после обрыва и продолжил ход. Rust требует `finish_reason` и `[DONE]`, поэтому завершил ход с `IncompleteStream` до запуска инструмента.

## Релизная проверка и замеры CLI

CLI v0.1.0 опубликован из тега на коммите `539fc7f`. Workflow загрузил оба архива и файлы SHA-256, затем сверил скачанные файлы с артефактами сборки. Отдельная проверка файлов из GitHub Releases подтвердила SHA-256, HTTPS с системными корнями, сохранение сессии, `--resume` и FTS в Debian 13 и Alpine 3.24.2 без Python. Опубликованный musl-бинарник также выполнил запрос к реальному HTTPS API из Alpine со штатным хранилищем CA. Репетиции переключения и возврата прошли с обоими скачанными бинарниками на одноразовых профилях. [Релиз v0.1.0](https://github.com/tsrman/hermes-rs/releases/tag/v0.1.0), [GitHub Actions](https://github.com/tsrman/hermes-rs/actions/runs/44885996089)

Release-бинарники коммита `93217e7` проверены на чистых образах `debian:trixie-slim` (Debian 13, GNU) и `alpine:3.24.2` (musl) без Python и Cargo внутри контейнера CLI. Для обеих целей подтверждены запись файла из интерактивного терминала, перезапуск локального владельца, `--resume` по тому же ID, чтение сохранённой истории и поиск по ней. Бинарник musl собран как статический PIE. В имитаторе использовались синтетические запросы.

В отдельной проверке модель `deepseek-flash-free` через настроенный OpenAI-compatible HTTPS-шлюз вернула ожидаемый текст. GNU-сборка получила первые данные в stdout через 2,73 с, команда завершилась через 2,80 с. ## Разбор конфига по правилам эталона

Сверено с эталоном и записано в фикстурах: раскрытие `${VAR}` и `${env:VAR}` во всех строковых значениях `config.yaml` (11 входов против `_expand_env_vars`), именованные провайдеры `providers:`/`custom_providers:` по ключу или имени с `base_url`, `api_key`, `key_env`, `api_mode`/`transport` и `model` записи (15 случаев `resolve_runtime_provider`, `compat/create_named_provider_fixture.py`), порядок ключей `--api-key` > `model.api_key` > `HERMES_API_KEY`. `extra_body` записи провайдера отправляется в запросах основного хода на всех транспортах и не отправляется в запросе на сжатие (в эталоне там только `auxiliary.compression.extra_body`), `extra_headers` и `model.default_headers` отправляются везде и не попадают в журнал. ## Проверка и миграция профиля

`profile check` и `profile migrate` проверены на профилях, сгенерированных историческим Python `SessionDB` и текущим Python API. Из схемы 32 перенесены 4 сессии и 6 сообщений в схему 33. Сквозные тесты проверяют перенос зафиксированных записей WAL, инвентаризацию прав без раскрытия секретов, приватные права копии, сохранность настроек, памяти и навыков, выбор именованного профиля и блокировку при повреждённом FTS, символической ссылке или существующем каталоге назначения. ## Контрольный возврат на Python

Репетиция выполнена на одноразовых профилях для релизных Linux x86_64 GNU и musl. Rust записал подтверждённый файл в продолжении исходной сессии и создал новую сессию с результатом `read_file`. Перед возвратом сохранён архив профиля после Rust.

- Python схемы 33 открыл базу с проверкой схемы, передал пары вызовов и результатов в запросы модели и через `AIAgent` продолжил обе сессии под прежними ID. Поиск FTS нашёл оба добавленных хода.
- Для Python схемы 32 восстановлена копия снимка до миграции. Экспорт из Python схемы 33 импортировал новую сессию под прежним ID. Импорт пропустил существующую сессию, а повторный импорт пропустил оба ID. Исторический Python продолжил импортированную сессию, и новый ход найден через FTS. Поздний Rust-ход существующей сессии доступен в архиве схемы 33.
- Подтверждённый файл сохранил содержимое, inode и время изменения. Байты исходных баз и архивов Rust совпали до и после возврата.
